# Журнал согласий на обработку ПДн + починка `sendmail.php`

**Сайт:** es-trans.ru
**Дата:** 2026-08-18, выложен 2026-08-25
**Статус:** ✅ **на проде**, все 6 шагов пройдены и проверены снаружи.
Оба 🔴 закрыты: ч. 1 ст. 19 (пароль вынесен из веб-доступной директории)
и ч. 1 ст. 9 (согласие проверяется на сервере и пишется в журнал).
Инцидент при выкладке и его причина — D-005 в `docs/decisions.md`.

## Зачем

Формы `form-customs`, `form-offer`, `form-driver` отправляют заявки на
`files/sendmail/sendmail.php`, то есть **в почту**. Факт согласия на обработку
ПДн при этом **не сохранялся нигде**: поле `agreement` приходило в `$_POST`,
но в коде обработчика не упоминалось ни разу.

По ч. 1 ст. 9 152-ФЗ **обязанность доказать наличие согласия лежит на
операторе**. Письмо в почтовом ящике доказательством не является: его можно
удалить, ящик — перенести. Нужна запись: кто, когда, на что согласился и
какой текст при этом видел.

Форма на главной странице работает через Битрикс24 и там согласия хранятся
в CRM — этот патч закрывает **остальные три формы**.

## Что в патче

| Файл | Куда |
|---|---|
| `sendmail.php` | заменить `public_html/files/sendmail/sendmail.php` |
| `config.sample.php` | переименовать в `es-trans-config.php`, положить **вне** `public_html` |

## Что исправлено, кроме согласий

При разборе файла нашлось ещё пять проблем — они правятся тем же заходом,
потому что трогаем один и тот же файл.

### 1. 🔴 Пароль от почты в открытом виде

```php
$mail->Password = 'es-trans#2025';
```

Лежал в веб-доступной директории и передавался в переписке.
**Пароль скомпрометирован — сменить в панели Timeweb.** Новый вписывать
только в конфиг вне `public_html`, не в код.

Относится к ч. 1 ст. 19 152-ФЗ (обязанность принимать меры защиты ПДн):
реквизиты канала, по которому идут персональные данные, хранились незащищённо.

### 2. 🔴 Согласие не проверялось на сервере

Проверка была только через `required` в HTML. Обходится отключением JS или
прямым POST-запросом — и тогда данные обрабатывались бы без согласия
(ч. 1 ст. 9 152-ФЗ). Теперь без `agreement` запрос отклоняется.

### 3. 🟡 Защита от ботов отключена

```php
/* if ($_POST['code'] != 'NOSPAM') { exit; } */
```

Закомментировано. Заменено на honeypot — скрытое поле `website`, которое
заполняют только боты. Не требует ключей и сторонних сервисов, не мешает
доступности. Прежний вариант `code=NOSPAM` защищал слабо: значение зашито
в HTML и читается любым парсером.

### 4. 🟡 XSS в письме

Значения из `$_POST` вставлялись в HTML-письмо без экранирования —
отправитель мог протащить разметку или подделать вид письма. Добавлен
`htmlspecialchars()`. Проверено: `<img src=x onerror=alert(1)>` приходит
как текст.

### 5. 🟡 Условия всегда истинны

```php
if (trim(!empty($_POST['company-name-customs'])))
```

Скобка не на месте: `!empty(...)` даёт `true`, `trim(true)` даёт `"1"` —
истину. Условие срабатывало всегда, в письмо попадали пустые строки.
Правильно: `!empty(trim($_POST[...] ?? ''))`.

## Порядок выкладки

Делать **в этом порядке** — если поменять местами, формы временно перестанут
работать.

### Шаг 1. Сменить пароль почты

Панель Timeweb → Почта → `main@es-trans.ru` → сменить пароль.
Сделать это **до** остального.

### Шаг 2. Создать таблицу

phpMyAdmin → выбрать базу → вкладка SQL → вставить содержимое `schema.sql`
→ выполнить. Если базы ещё нет — создать в панели Timeweb (кодировка
`utf8mb4_unicode_ci`).

### Шаг 3. Положить конфиг вне public_html

Структура на Timeweb обычно такая:

```
/home/uXXXXX/es-trans.ru/
    public_html/          <- сюда смотрит веб-сервер
        files/sendmail/sendmail.php
    config/               <- создать
        es-trans-config.php
```

Заполнить новым паролем почты и реквизитами БД. Выставить `chmod 600`.

**Проверить, что файл недоступен снаружи:** открыть
`https://es-trans.ru/config/es-trans-config.php` — должно быть 404.
Если открылся — файл положен не туда, немедленно переместить.

### Шаг 4. Добавить honeypot в вёрстку

В каждую из трёх форм (`form-customs`, `form-offer`, `form-driver`) добавить
фрагмент из `form-honeypot.html` перед кнопкой отправки. Формы продублированы
постранично — нужна **полная пересборка Gulp**, как обычно.

### Шаг 5. Заменить sendmail.php

Скопировать `sendmail.php` из патча в `public_html/files/sendmail/`.
Директорию `phpmailer/` не трогать — она используется как прежде.

> **Заливать файлом, не вставкой в редактор.** Первая строка обязана быть
> ровно `<?php declare(strict_types=1);` — без пустой строки и без BOM перед
> ней. Если `declare` окажется не первой инструкцией, PHP отдаёт
> **HTTP 500 с пустым телом** на любой запрос, и формы лягут целиком.
> Так уже случилось на es-trans.ru 25.08 (см. D-005 в `docs/decisions.md`).

> **Включите логи до выкладки.** На Timeweb `error_log` по умолчанию
> **выключен** (панель → Логи → тумблеры по домену), файл появляется в
> `~/<домен>/`. Без него 500-я непрозрачна: тело пустое, в `access_log`
> только код ответа.

### Шаг 6. Проверить

1. Отправить тестовую заявку из каждой формы → письмо пришло, в нём внизу
   блок «Согласие на обработку ПДн: получено».
2. phpMyAdmin → `SELECT * FROM consents ORDER BY id DESC LIMIT 5` → записи есть.
3. Снять галочку согласия и попробовать отправить → форма не отправляется
   (проверка на клиенте). Это ожидаемо.

После выкладки напишите — прогоню Playwright-проверку всех трёх форм.

## Что проверено локально

PHP 8.2, стенд со стабом PHPMailer, 8 сценариев. **Тестировать нужно на той
версии PHP, что стоит у клиента** — на es-trans.ru это PHP 7.4:

| Сценарий | Ожидание | Факт |
|---|---|---|
| Водитель, согласие есть | письмо + запись | ✅ |
| Водитель, согласия нет | отказ, письма нет | ✅ |
| Заполнен honeypot (бот) | тихий «успех», письма нет, записи нет | ✅ |
| Пустой запрос | отказ | ✅ |
| XSS в имени | экранировано | ✅ |
| Растаможка, согласие есть | письмо + запись | ✅ |
| Растаможка с чужим чекбоксом | отказ | ✅ |
| Вакансии, согласие есть | письмо + запись | ✅ |

Отдельно проверено: при недоступной БД запись уходит в резервный файл
(`consents-fallback.log`), заявка при этом не теряется, а в письме появляется
пометка о сбое записи. Схема `schema.sql` проверена на движке SQL — 13 колонок,
вставка и поиск по телефону работают.

Замечание, найденное тестом: изначально использовался `mb_substr`, но
расширение `mbstring` есть не на каждом хостинге. Заменено на собственную
функцию `cut()`, корректно обрезающую UTF-8 по границе символа.

## Важное про версию текста согласия

В конфиге есть поля `version` и `text`:

```php
'version' => '2026-08-18',
'text'    => 'Я даю согласие на обработку моих персональных данных…',
```

**Их нужно менять при каждой правке формулировки согласия** — в форме,
Политике или Соглашении. Иначе нельзя доказать, какую именно редакцию
человек видел: если он согласился 12 августа, а вы предъявите текст
от 18-го, доказательство рассыпается.

Вы уже дважды правили документы за последнюю неделю — то есть это не
теоретический риск. Рекомендуется хранить архив редакций Политики
и Соглашения (хотя бы копии файлов с датой в имени).

## Чего патч НЕ делает

- **Не переносит старые заявки.** Согласия, полученные до выкладки, нигде
  не зафиксированы и восстановлению не подлежат.
- **Не закрывает организационные требования.** Договор поручения на
  обработку (ч. 3 ст. 6 152-ФЗ) с Яндексом, Битрикс24 и Timeweb по-прежнему
  нужен.
- **Не меняет форму на главной** — она на Битрикс24, согласия хранятся в CRM.
- **Не настраивает бэкап БД.** Журнал согласий стоит включить в резервное
  копирование, иначе доказательства теряются вместе с базой.
