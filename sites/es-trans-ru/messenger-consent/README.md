# Уведомление о переходе в мессенджер (Telegram / MAX) — инструкция

## Контекст

На сайте есть ссылки на Telegram и MAX (проверено на живом проде,
`curl https://es-trans.ru/` и `services-customs.html`):

```html
<a class="social__link" target="_blank" href="https://max.ru/u/...">
<a class="chatme__link" href="https://t.me/+79096614874" target="_blank">
```

Судя по идентичному виду на разных страницах, это общий партиал,
инклюдится на каждую страницу сайта (тот же паттерн, что был с
cookie-баннером и формой Bitrix24).

Переход по такой ссылке — это переход на стороннюю платформу
(Telegram/MAX), где дальнейшее общение будет обрабатываться уже по
правилам этой платформы. С пользователем согласован **вариант 3**:
модалка-подтверждение с текстом про обработку персональных данных,
показывается один раз на каждый мессенджер (решение запоминается в
`localStorage`), при повторных переходах не мешает.

## Согласованное с пользователем поведение

- Клик по ссылке на Telegram ИЛИ MAX → реальный переход блокируется →
  показывается модалка: «Вы переходите в Telegram/MAX. Общаясь с нами
  в мессенджере, вы соглашаетесь с Политикой конфиденциальности и
  Соглашением об обработке данных» + кнопки «Отмена» / «Перейти».
- Переход происходит только после клика на «Перейти» — в новой вкладке,
  если у исходной ссылки был `target="_blank"` (сохраняет текущее
  поведение), иначе в текущей.
- Согласие на каждый мессенджер запоминается ОТДЕЛЬНО (два разных ключа
  `localStorage`) — если пользователь один раз подтвердил переход в
  Telegram, повторные клики по ссылкам на Telegram (на любой странице
  сайта) больше не показывают модалку. Для MAX — независимо.
- Работает для ЛЮБОГО количества ссылок на любых страницах — скрипт не
  ищет ссылки по конкретному CSS-классу, а перехватывает клики по всему
  документу и проверяет `href` на соответствие домену `t.me`/`telegram.me`
  (Telegram) или `max.ru` (MAX). Если понадобится добавить ещё одну
  ссылку на любой мессенджер в будущем — ничего в JS менять не нужно.

## Шаг 1 — загрузить файлы на сервер сайта

Положить рядом с существующими `css/style.min.css` и `js/app.min.js`:

- `messenger-consent.css` → `css/messenger-consent.css`
- `messenger-consent.js` → `js/messenger-consent.js`

## Шаг 2 — подключить перед `</body>`

Рядом с существующим подключением `cookie-banner.js` (это независимая
фича, порядок подключения относительно cookie-banner значения не имеет):

```html
<link rel="stylesheet" href="css/messenger-consent.css">
<script src="js/messenger-consent.js" defer></script>
```

HTML ссылок на Telegram/MAX менять не нужно — скрипт сам находит и
перехватывает клики по ним.

## Шаг 3 — проверить

1. Открыть сайт в приватном окне (чистый `localStorage`).
2. Кликнуть на ссылку Telegram (иконка/кнопка чата) — переход НЕ должен
   произойти сразу, вместо этого должна появиться модалка с текстом про
   Telegram, ссылками на «Политику конфиденциальности» и «Соглашение», и
   кнопками «Отмена» / «Перейти».
3. Нажать «Отмена» — модалка закрывается, вкладка Telegram не
   открывается.
4. Кликнуть на ту же ссылку ещё раз, нажать «Перейти» — должна открыться
   новая вкладка с Telegram (или `tg://`-переход, в зависимости от
   устройства/браузера — это поведение самой ссылки `t.me/...`, скрипт
   его не меняет).
5. Кликнуть на ссылку Telegram ещё раз (третий раз) — модалка НЕ должна
   появляться повторно, переход должен происходить сразу (согласие уже
   запомнено).
6. Очистить `localStorage`, повторить шаги 2-5 для ссылки MAX — должно
   вести себя независимо от Telegram (можно принять MAX, но продолжать
   видеть модалку для Telegram, если Telegram ещё не подтверждали).
7. Проверить на странице `services-customs.html` (или любой другой,
   отличной от главной) — модалка должна появляться там же, без
   дополнительной настройки, а согласие, данное на главной странице,
   должно быть уже учтено (общий `localStorage` на домен).

Проверить на живом проде можно через `playwright-skill`, по аналогии с
прошлыми проверками (см. `docs/changelog.md`).

## Известный баг и фикс (2026-08-13)

После первого деплоя обнаружилось: в модалке вторая ссылка
(«Соглашением об обработке данных») не рендерилась как ссылка — вместо
неё был виден сырой экранированный HTML.

**Уточнение причины** (по факту, после сверки с реальным `script.js`
сайта): никакого отдельного скрипта-сканера, автоматически
расставляющего `data-lang`, на сайте нет — атрибуты `data-lang`
прописываются **вручную прямо в коде**, как в `cookie-banner.js`
(`<span data-lang="cookie-banner-1">...`). Проблема была не в
локализации, а в самой строке `innerHTML` модалки — версия с двумя
одинаковыми `class="messenger-consent__link"` подряд собиралась не так
аккуратно, как у cookie-banner, из-за чего вторая ссылка сломалась при
рендере.

Исправлено: модалка теперь собирается через DOM-методы
(`document.createElement`/`appendChild`) вместо строки `innerHTML`, а
`data-lang` (`messenger-consent-1` … `messenger-consent-8`) проставлены
на каждый узел вручную через `setAttribute` — по той же нумерации и
той же логике, что и в `cookie-banner.js`. Файл `messenger-consent.js`
в этой папке уже содержит фикс.

**Важно при обновлении на сервере:** в присланном `script.js` в реальный
файл сайта, судя по всему, попало НЕСКОЛЬКО копий блока
messenger-consent подряд (старая версия с багом дважды + фрагмент
неиспользуемого кода из промежуточной правки). Нужно удалить ВСЕ старые
копии блока `/* Уведомление о переходе в мессенджер... */ (function () {...})();`
и оставить в файле только одну — актуальную версию из
`messenger-consent.js` в этой папке.

Как и для остальных патчей на этом сайте — это техническая реализация,
не юридическая консультация. Формулировка текста и то, достаточно ли
