# Бэкап журнала согласий — таблица `consents`

**Сайт:** es-trans.ru
**Дата:** 2026-08-26
**Статус:** инструкция для владельца, кода на сайте не меняет

## Зачем

Таблица `consents` — **единственное доказательство** того, что человек дал
согласие на обработку своих ПДн. По **ч. 1 ст. 9 152-ФЗ** доказывать наличие
согласия обязан оператор: нет записи — согласия юридически не было, даже если
галочка стояла и заявка пришла в почту. Письмо в ящике доказательством не
является (там нет ни текста согласия, ни его версии, ни подтверждения, что
человек видел именно эту редакцию).

Потеря базы = откат обоих закрытых 🔴 обратно в открытые, причём
восстановить нечем: согласия, полученные до 25.08, и так нигде не
зафиксированы.

## Что уже работает само

**Timeweb делает автоматический бэкап баз данных каждую ночь и хранит
30 дней.** Включать ничего не нужно, это штатное поведение виртуального
хостинга. Смотреть: панель управления → **«Резервные копии»** → вкладка
**«Базы данных»** → выбрать дату.

Значит задача не «настроить бэкап с нуля», а закрыть **три разрыва**, которые
ночной автобэкап не покрывает.

---

## Разрыв 1. Никто не проверял, что бэкап реально существует

Автобэкап — обещание хостера, а не проверенный факт. Пока копию не открыли
глазами, неизвестно, попадает ли в неё нужная база и есть ли там таблица
`consents` (база `cb10291_privacy` создавалась 25.08, отдельно от основной
`cb10291_estrans1`).

**Сделать один раз, 5 минут:**

1. Панель Timeweb → «Резервные копии» → вкладка «Базы данных».
2. Выбрать вчерашнюю дату.
3. Найти базу **`cb10291_privacy`** и двойным кликом по имени раскрыть
   список таблиц.
4. Убедиться, что в списке есть **`consents`**.

> Имя базы `cb10291_privacy` взято со скриншота phpMyAdmin от 26.08 — сверьте
> с тем, что стоит в `es-trans-config.php` → `db.name`. В аккаунте есть ещё
> `cb10291_estrans1` и `cb10291_copy`; согласия лежат **только** в
> `cb10291_privacy`, и бэкапить нужно именно её.

Если базы `cb10291_privacy` в списке нет — значит она по какой-то причине не
попадает в автобэкап, и дальше всё держится только на ручных копиях
(разрыв 3). Это надо выяснить в поддержке Timeweb до того, как копия
понадобится.

## Разрыв 2. Горизонт 30 дней против срока хранения согласий

Автокопии живут **30 дней**. Согласие действует и должно быть доказуемо
**всё время обработки данных плюс срок хранения** — это годы, а не месяц.

Сценарий, в котором 30 дней не спасают: таблицу почистили/сломали в марте,
заметили в мае — все автокопии, где данные ещё были, уже удалены. Проверка
РКН или запрос субъекта приходят как раз с задержкой в месяцы.

**Что делать — квартальный архивный дамп**, который хранится не на хостинге.
Раз в 3 месяца (и обязательно **перед любой правкой таблицы**):

**Через phpMyAdmin, без SSH:**

1. Открыть phpMyAdmin → база `cb10291_privacy` → таблица `consents`.
2. Вкладка **«Экспорт»** → способ «Обычный» → формат **SQL**.
3. В блоке «Кодировка» оставить `utf8mb4`, в «Формат» — SQL.
4. Нажать «Вперёд» — скачается файл `consents.sql`.
5. Переименовать по шаблону **`consents-YYYY-MM-DD.sql`** и положить туда,
   где данные переживут потерю хостинга: рабочий компьютер + облако или
   внешний диск. **Не в тот же аккаунт Timeweb** — иначе одна проблема
   уносит и базу, и копию.

**Через SSH (если доступ есть) — то же самое одной командой:**

```bash
mysqldump -u'ПОЛЬЗОВАТЕЛЬ' -p'ПАРОЛЬ' cb10291_privacy consents \
  --no-tablespaces --default-character-set=utf8mb4 \
  > consents-$(date +%F).sql
```

⚠️ Пароль в командной строке виден в истории команд и в списке процессов.
На разовой операции терпимо; если делать регулярно — вынести доступы в
`~/.my.cnf` с правами 600 и запускать `mysqldump --defaults-file=~/.my.cnf`.

⚠️ **Дамп содержит персональные данные** — имена, телефоны, e-mail, IP. Это
такой же носитель ПДн, как сама база: хранить в защищённом месте, не
пересылать почтой и мессенджерами, не класть в общие папки. Меры защиты при
хранении — ч. 1 ст. 19 152-ФЗ, та самая статья, по которой закрывали пароль
в коде.

## Разрыв 3. Резервный лог не бэкапится вместе с базой

В конфиге (`es-trans-config.php`) есть путь:

```php
'fallback_log' => __DIR__ . '/consents-fallback.log',
```

Это второй носитель согласий: когда база недоступна, обработчик пишет
согласие сюда, чтобы оно не потерялось. Файл лежит **вне `public_html`**,
рядом с конфигом.

Два следствия, которые легко упустить:

- Файл попадает в бэкап **файлов**, а не баз данных — это отдельная вкладка
  в панели. Если восстанавливать только базу, согласия из периода сбоя
  потеряются.
- **В файле лежат ПДн открытым текстом.** Права на него должны быть такими
  же строгими, как на конфиг (600), и он не должен быть доступен по HTTP.

**✅ Проверено снаружи 26.08.2026 — файл не отдаётся по HTTP.** Прогнаны
шесть путей, все вернули **404**:

```
404  https://es-trans.ru/consents-fallback.log
404  https://es-trans.ru/files/sendmail/consents-fallback.log
404  https://es-trans.ru/files/consents-fallback.log
404  https://es-trans.ru/consents.sql
404  https://es-trans.ru/files/sendmail/config.php
404  https://es-trans.ru/es-trans-config.php
```

Утечки нет. Перепроверять этой же командой **после каждой пересборки сайта**
— если файл случайно окажется внутри `public_html`, журнал согласий сможет
скачать кто угодно, а это уже утечка ПДн, а не отсутствие бэкапа.

**Заодно посмотреть, не накопилось ли в нём записей:**

непустой `consents-fallback.log` означает, что база в какой-то момент была
недоступна и часть согласий существует **только** в этом файле. Их надо
перенести в таблицу, иначе поиск по субъекту (ст. 14) их не найдёт.

## Проверка восстановления

Бэкап, который ни разу не разворачивали, — это предположение о бэкапе.
Проверить можно безопасно, не трогая рабочую таблицу:

```sql
-- Развернуть дамп в отдельную таблицу и сравнить количество записей
CREATE TABLE consents_restore_test LIKE consents;
-- (загрузить дамп в consents_restore_test через phpMyAdmin → Импорт)

SELECT COUNT(*) FROM consents;
SELECT COUNT(*) FROM consents_restore_test;

DROP TABLE consents_restore_test;   -- убрать после сверки
```

Числа должны совпасть (с поправкой на заявки, пришедшие после снятия дампа).

## Что эта инструкция НЕ закрывает

- **Согласия до 25.08.2026** — не фиксировались нигде, восстановлению не
  подлежат ни бэкапом, ни чем-либо ещё.
- **Хранение самих дампов** — за пределами хостинга это уже зона
  ответственности владельца: где лежат, кто имеет доступ, шифруются ли.
- **Срок хранения согласий** — отдельный вопрос: по ч. 5 ст. 21 152-ФЗ ПДн
  уничтожаются в течение 30 дней после отзыва согласия или достижения цели.
  Значит бэкапы тоже не могут храниться вечно «на всякий случай» — при
  отработке отзыва запись должна исчезать и из актуальной базы, и из архивных
  копий при их следующей ротации.
