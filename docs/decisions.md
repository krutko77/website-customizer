посторонних сетевых вызовов и `exec`. По этому критерию отклонены
`willmarple/playwright-skill` (7★) и `akaihola/playwright-py-skill` (3★).

**Последствия.** `package.json` остался без зависимостей — стек выбирается
под конкретную задачу. `deploy-vps.sh` сохранён (универсальный деплой на
VPS), но применим только если появится серверная часть.

## D-003 · Проверка браузерной автоматизации: блокер снят
**Дата:** 2026-08-11 · **Статус:** принято

**Контекст.** Прошлый снимок фиксировал, что Chromium не запускается —
`npx playwright install-deps chromium` требует root, а `sudo` в окружении
нет.

**Проверка.** Запустили headless Chromium напрямую через `playwright`
внутри `.claude/skills/playwright-skill/` (там уже стоит `npm install`) —
браузер стартовал и загрузил страницу без доустановки системных библиотек.

**Решение.** Считаем блокер снятым: `install-deps` действительно падает
без root, но нужные библиотеки уже есть в образе, и обычный
`npx playwright install chromium` (без `-deps`) плюс `npm install` в
папке скилла достаточны для работы.

**Последствия.** `playwright-skill` и `webapp-testing` пригодны к
использованию. Если в будущем понадобятся firefox/webkit — их запуск
нужно проверять отдельно, гарантии на них эта проверка не даёт.

## D-004 · Журнал согласий: MySQL-таблица, а не лог-файл и не Битрикс24

**Дата:** 2026-08-18
**Статус:** принято

**Контекст.** Три формы es-trans.ru (`form-customs`, `form-offer`,
`form-driver`) шлют заявки на `sendmail.php`, то есть в почту. Факт согласия
на обработку ПДн не сохранялся нигде: поле `agreement` приходило в `$_POST`,
но в обработчике не упоминалось. По ч. 1 ст. 9 152-ФЗ доказывать наличие
согласия обязан оператор; письмо в ящике доказательством не является.

**Рассмотренные варианты.**
1. Лог-файл JSON Lines вне `public_html` — быстро, но поиск и удаление по
   конкретному субъекту вручную.
2. **Таблица MySQL** — выбрано.
3. Перевести все формы на Битрикс24 — согласия хранились бы в CRM
   единообразно, но формы меняются визуально и добавляется зависимость от
   Битрикса там, где её сейчас нет.

**Решение.** Вариант 2 + файл как резервный путь при недоступности БД.

**Почему.** Хранение — половина задачи. По ст. 14 субъект вправе запросить
сведения о своих данных, по ст. 21 — удаление. По лог-файлу это греп и ручная
правка, по таблице — обычный запрос с индексом по телефону и e-mail. При
десятке заявок разницы нет, при тысяче она решающая.

**Побочно зафиксировано в том же патче** (`sites/es-trans-ru/consent-log/`):
пароль SMTP лежал открытым текстом в веб-доступной директории (скомпрометирован,
подлежит смене — ч. 1 ст. 19 152-ФЗ), проверка согласия была только клиентской,
антибот закомментирован, XSS в HTML-письме, и условия вида
`trim(!empty($x))`, истинные всегда.

**Ключевое требование эксплуатации.** Поля `consent.version` и `consent.text`
в конфиге обязаны меняться при каждой правке формулировки согласия — иначе
нельзя доказать, какую редакцию видел человек. Политика и Соглашение уже
правились дважды за неделю, риск не теоретический.

## D-005 · Выкладка `sendmail.php`: `declare(strict_types=1)` в первой строке, `require` через `__DIR__`

**Дата:** 2026-08-25
**Статус:** принято, проверено на проде

**Контекст.** После выкладки нового `sendmail.php` (патч `consent-log/`, шаг 5)
все три формы легли: любой запрос — GET, пустой POST, полный POST — отдавал
**HTTP 500 с нулевым телом**. Заявки не уходили ни в почту, ни в базу.
Диагностика заняла несколько итераций, потому что логи на хостинге были
**выключены** и причину приходилось угадывать.

**Что оказалось.** После включения `error_log` строка нашлась сразу:

```
PHP Fatal error: strict_types declaration must be the very first statement
in the script ... sendmail.php on line 3
```

В патче `declare(strict_types=1)` стоял на строке 18 — после шапки-комментария,
что синтаксически законно. При заливке на хостинг шапка потерялась, `declare`
оказался на строке 3, и перед ним осталась пустая строка. PHP это запрещает
безусловно: `declare(strict_types)` обязан быть **первой инструкцией**, и
комментарий перед ним допустим, а пустая строка после `<?php` — нет.

**Решение.**
1. `declare` перенесён в **первую строку вместе с открывающим тегом**:
   `<?php declare(strict_types=1);` — уехать на другую строку он теперь не может
   физически, каким бы редактором файл ни заливали.
2. Все `require` PHPMailer переведены на абсолютные пути через `__DIR__`
   (было `require 'phpmailer/src/PHPMailer.php'`), туда же — `setLanguage()`.

**Почему второе, если падало из-за первого.** Относительный `require` ищет файл
от **рабочей директории процесса**, а не от папки скрипта. Лог показал
`sapi_apache2.c` — сайт работает под Apache (nginx стоит фронтом), и там рабочая
директория при `require` не совпадает с папкой скрипта. До этой ошибки просто
не дошло: скрипт падал раньше, на строке 3. Исправлено вместе, чтобы не ловить
второй раунд 500-х.

**Уроки на будущее.**
- **Логи включать до выкладки, а не после.** На Timeweb `access_log` и
  `error_log` по умолчанию **выключены** (панель → Логи → тумблеры по домену,
  файл появляется в `~/<домен>/`). Без них 500-я непрозрачна: тело пустое,
  в `access_log` только код ответа. Три итерации гаданий против одной строки лога.
- **Не считать «синтаксически законно» достаточным для файла, который поедет
  через чужой буфер обмена.** Конструкции, чувствительные к позиции в файле
  (`declare`, отсутствие BOM, отсутствие пустой строки перед `<?php`), надо
  делать устойчивыми к копированию, а не полагаться на аккуратность заливки.
- **Относительные `require` в патчах не использовать** — целевое окружение
  (Apache/FPM, рабочая директория) заранее неизвестно.

**Проверено снаружи после исправления** (curl, 25.08): GET → «Метод не
поддерживается»; пустой POST → «Форма пуста»; POST без `agreement` (driver и
customs) → **отказ**; POST с чужим чекбоксом (`agreement` вместо
`agreement-customs`) → отказ; POST с согласием → принят; honeypot заполнен →
тихий «успех»; конфиг по 6 путям → 404; пароля в исходнике нет.

## D-006 · Защита от ботов: сначала измерить поток, потом выкладывать

**Дата:** 2026-08-26 · **Статус:** принято

**Контекст.** 26.08 в журнале согласий найдена запись id 2 — заявка бота,
пришедшая прямым POST в `sendmail.php` мимо страницы формы (`page_url` =
главная, хотя `form-customs` открывается только с `services-customs.html`).
Дефект воспроизведён на проде: голый `curl` без `Referer` с `agreement=on`
принимается. Патч `sites/es-trans-ru/bot-post-fix/` написан и проверен в
тот же день (24/24, негативный прогон ловит регрессию).

**Варианты.**
1. Выложить патч сразу — риск закрыт немедленно.
2. **Подождать пару дней, посмотреть частоту атак по журналу, потом решать.**
3. Не чинить вовсе.

**Решение.** Вариант 2, выбрал владелец. `sendmail.php` пока не меняется.

**Почему.** Известен ровно **один** случай за сутки — этого мало, чтобы
судить о потоке. Правка меняет файл, через который проходят **все** заявки
с сайта, а характерный отказ у неё тихий: при слишком строгой проверке
пользователь видит «успех», а заявка не доходит. Менять такой файл ради
недоказанной проблемы — риск больше выгоды. Через пару дней журнал сам
покажет, разовый это залёт или поток.

**Последствия.**
- До выкладки журнал согласий продолжает пополняться записями ботов. По
  ч. 1 ст. 9 152-ФЗ таблица служит доказательством реальных согласий, так
  что мусор в ней — накапливающийся, а не статичный минус.
- Критерий для решения: считать записи с `page_url`, не совпадающим со
  страницей своей формы. Запрос — в `state.md`.
- Патч **не устаревает** от ожидания: он не зависит от версии текста
  согласия и вёрстки, меняется только `sendmail.php`.
- При выкладке обязателен прогон живых форм через браузер
  (`docs/checklists/live-forms-e2e-check.md`), а не только curl — тихий
  отказ иначе не заметить.
