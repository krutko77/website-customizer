## 2026-08-12 — Bitrix24-патч: баг рендера формы найден и исправлен, финальная проверка на проде
- Клиент применил патч отложенной загрузки формы Bitrix24 (см. запись
  ниже) и задеплоил, но при проверке в инкогнито обнаружил баг: после
  нажатия «Принимаю» cookie появлялись, заглушка пропадала, но вместо
  формы в попапе было пусто
- Диагностировано Playwright'ом (проверка DOM-путей `.b24-form` после
  клика на «Принимаю»): виджет Bitrix24 рендерился внутри `<head>`
  страницы, а не в попапе. Причина — скрипт `loader_16.js` вставлялся
  через `getElementsByTagName('script')[0].parentNode.insertBefore(...)`
  (первый `<script>` страницы, обычно в `<head>`); с атрибутом
  `data-skip-moving="true"` виджет рендерит себя рядом с тем DOM-узлом,
  где физически лежит его `<script>`-тег — в оригинальном инлайн-варианте
  это работало, потому что скрипт лежал прямо внутри `.popup__text`
- Исправлено: скрипт теперь вставляется `mount.appendChild(s)` — прямо
  внутрь `#b24-form-mount` (placeholder-диву в попапе). Проверено
  изолированным тестом на локальном HTML: после фикса форма (6 полей
  ввода) рендерится именно внутри mount-элемента
- По запросу пользователя создан отдельный готовый к вставке в Gulp-сборку

  было собирать патч из диффов в README вручную. README дополнен врезкой

- Разобран вопрос пользователя: что если посетитель не нажимает ни одну
  кнопку — объяснено (без изменения кода), что это осознанное
  opt-in-поведение: баннер остаётся на экране, `localStorage` не
  заполняется, Метрика не стартует, баннер появляется заново при каждом
  визите, пока пользователь не сделает выбор
- Уточнение по запросу «заблокировать сайт до выбора cookie»: пользователь
  сначала попросил такую блокировку, но в кларифай-вопросах явно ответил
