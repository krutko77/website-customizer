  реально собираемые поля форм

  `services-customs.html` и спросил, что это — первая гипотеза (у сайта

## 2026-08-12 — Cookie-баннер es-trans.ru: фикс IIFE-бага, проверка на проде, мобильный фикс
- Выяснилось, что реальные исходники сайта клиента живут в отдельном
  Gulp-проекте на его ноутбуке (`es_trans_china`), вне доступа этой среды —
  дальнейшая работа идёт через текстовые патчи в чате, а не прямые правки
  файлов; клиент сам вносит и пересобирает через Gulp
- Разобран пасток клиента: cookie-баннер не запускался из-за бага в
  `script.js` — IIFE была объявлена, но не вызывалась (`});` вместо
  `})();`), из-за чего весь код баннера (включая `start()`) был мёртвым.
  Клиент исправил на своей стороне, подтверждено сверкой второй присылки
  файла
- После фикса выполнена полная Playwright-проверка на живом проде
  (`https://es-trans.ru/`, headless, чистый контекст) — оба сценария
  подтверждены 6/6 по каждому: баннер появляется при первом визите,
  `mc.yandex.ru/watch` не уходит до согласия, после «Принимаю» — уходит и
  баннер скрывается, после «Отказаться» — счётчик не уходит вообще,
  решение (`accepted`/`declined`) сохраняется в `localStorage` и баннер
  не показывается повторно после перезагрузки в обоих случаях
- Разобран вопрос пользователя: что если посетитель не нажимает ни одну
  кнопку — объяснено (без изменения кода), что это осознанное
  opt-in-поведение: баннер остаётся на экране, `localStorage` не
  заполняется, Метрика не стартует, баннер появляется заново при каждом
  визите, пока пользователь не сделает выбор
- Уточнение по запросу «заблокировать сайт до выбора cookie»: пользователь
  сначала попросил такую блокировку, но в кларифай-вопросах явно ответил
  «блокировку не делаем вообще» — запрос отменён, код не менялся
- Клиент сообщил о новом баге: на мобильной версии (390–430px) баннер
  занимал почти весь экран по высоте. Причина найдена по скриншотам
  DevTools пользователя: `.cookie-banner__text` в мобильном медиа-запросе
  наследовал `flex-basis: 480px` от десктопного правила `flex: 1 1 480px`,
  а при `flex-direction: column` (мобильный layout) `flex-basis` работает
  по высоте, а не по ширине — отсюда раздутый баннер
- Патч передан текстом: внутри `@media (max-width: 640px)` для
  `.cookie-banner__text` добавлено `flex: none` (плюс мелкая доводка
  паддингов/шрифта кнопок и текста). Клиент применил, пересобрал,
  подтвердил скриншотом — баннер теперь занимает высоту по контенту
- Тот же мобильный патч продублирован в каноническом файле-эталоне
  `sites/es-trans-ru/cookie-banner/cookie-banner.css` для консистентности
  (не является источником для клиентской сборки, но должен отражать
  актуальное состояние фичи)
- Cookie-баннер на этом можно считать полностью готовой и проверенной
  фичей — активных задач по нему не осталось

## 2026-08-11 — Диагностика: cookie-баннер не появляется на проде es-trans.ru
- Клиент выложил правки на прод самостоятельно, но сообщил, что баннер не
  появляется и ошибок в консоли нет
- Скачан актуальный HTML `https://es-trans.ru/` (`curl`) и сверен построчно
  с инструкцией `sites/es-trans-ru/cookie-banner/README.md`
- Найдена причина: выполнен только Шаг 2 инструкции (обёртка инициализации
  Метрики в `window.__esTransInitMetrika` — применена корректно). Шаг 1
  (загрузка `js/cookie-banner.js` и `css/cookie-banner.css` на сервер) и
  Шаг 3 (подключение этих файлов через `<link>`/`<script>` в HTML) не
  выполнены: оба файла отдают 404, тега подключения скрипта в HTML нет
  вообще. Старый сторонний баннер `cookieinfoscript.com` при этом уже
  удалён — сайт временно вообще без cookie-баннера
- Объяснено пользователю, почему нет ошибок в консоли: раз тег `<script>`
  отсутствует в HTML, браузер не делает запрос и 404 в Console не видно
  (видно было бы только в Network)
- Патч под актуальный HTML (`app.min.js?_v=20260811171125`) намечен, но
  не подготовлен в рамках сессии — следующий шаг
