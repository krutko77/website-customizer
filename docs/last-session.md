- После фикса клиент попросил проверить прод — выполнена полная
  Playwright-проверка на живом `https://es-trans.ru/` (headless, чистый
  контекст, без сохранённого localStorage):
  - сценарий «Принимаю»: баннер появляется, `mc.yandex.ru/watch` не
    уходит до клика, после клика — уходит и баннер скрывается, решение
    `accepted` сохраняется в localStorage, баннер не появляется повторно
    после reload — все проверки прошли
  - сценарий «Отказаться»: баннер скрывается, `mc.yandex.ru/watch` не
    уходит ни разу (ни до, ни после), решение `declined` сохраняется,
    баннер не появляется повторно после reload — все проверки прошли
- Отвечено на вопрос «что если посетитель не нажмёт ни одну кнопку» —
  без изменения кода: баннер остаётся видимым, `localStorage` не
  заполняется, Метрика не стартует, баннер показывается заново при
  каждом визите — это осознанный opt-in-дизайн, не баг
- По запросу «заблокировать сайт до выбора cookie» заданы уточняющие
  вопросы; ответы пользователя оказались противоположны исходному
  запросу («блокировку не делаем вообще») — блокировка отменена, код не
  менялся, поведение осталось прежним (баннер просто остаётся видимым)
- Клиент сообщил о новом баге: на мобильной версии (390–430px, iPhone 14
  Pro Max в DevTools) баннер занимал почти весь экран по высоте.
  По присланным скриншотам DevTools найдена причина: `.cookie-banner__text`
  в мобильном медиа-запросе (`@media max-width: 640px`,
  `flex-direction: column`) наследовал `flex-basis: 480px` от десктопного
  правила `flex: 1 1 480px` — при column-layout `flex-basis` считается по
  высоте, а не по ширине, отсюда раздутый баннер
- Передан текстовый патч: `flex: none` для `.cookie-banner__text` внутри
  мобильного медиа-запроса (плюс мелкая доводка паддингов и размера
  шрифта у текста/кнопок). Клиент применил, пересобрал Gulp, подтвердил
  скриншотом, что баннер теперь занимает нормальную высоту
- Тот же мобильный патч продублирован в каноническом файле-эталоне
  `sites/es-trans-ru/cookie-banner/cookie-banner.css` (для консистентности
  репозитория — не является источником сборки клиента)

## Ключевые решения
- Файлы клиента недоступны для прямого редактирования — весь фронтенд
  реппаунд по этому сайту идёт через текстовые патчи в чате и обратную
  связь по скриншотам/DevTools, а не через Edit/Write в этой среде
- Запрос на блокировку взаимодействия с сайтом до выбора cookie —
  отменён самим пользователем в ходе уточнения; текущее поведение
  (баннер просто остаётся видимым, ничего не блокируется) сохранено как
  окончательное

## Подводные камни
- Реальные файлы сайта клиента (Gulp-проект, `script.js`,
  `cookie-banner.scss` и т.д.) физически недоступны из этой среды —
  нельзя редактировать их напрямую через Edit/Write; любые правки нужно

  подтверждения применения от клиента
- Канонические файлы-эталоны в `sites/es-trans-ru/cookie-banner/` — не
  источник для реальной сборки клиента, а справочный образец в
  репозитории; их нужно вручную синхронизировать с патчами, которые
  реально ушли клиенту, иначе они разъедутся
- Эта VS Code-сессия Claude Code подключена через локальный
  shim-прокси (`ANTHROPIC_BASE_URL=http://172.30.0.1:8190`), не напрямую
  к аккаунту claude.ai — `/status` и панель Usage не показывают реальные
  лимиты/дату продления подписки; похоже на учебную/тренировочную
  песочницу
- `.env.example` — не гитигнорится, в отличие от `.env`. Секреты туда
  класть нельзя
- Прямые `fetch`-запросы к github.com заблокированы; GitHub — через
  `curl`/`git`. Обычные внешние сайты (включая es-trans.ru) через `curl`
  доступны без ограничений
- Запись в `.claude/commands/` требует python3, а не bash `cat` или Write
