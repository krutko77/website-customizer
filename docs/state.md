**00. `sites/es-trans-ru/consent-gating-fix/` — 🟡 ПОДГОТОВЛЕН, НА ПРОД
НЕ ВЫЛОЖЕН** (18.08.2026).

Задачу поставил пользователь: «в Политике отражены все типы куки, которые
используются на нашем сайте?». Аудит cookie **по каждой странице отдельно**
(а не только по главной, как раньше) нашёл два расхождения с разделом 7
Политики:

- **(А) Яндекс.Карта на `contacts.html`** ставила 11 cookie `.yandex.ru`
  (`yandexuid`, `yuidss`, `i`, `pi`, `bh`, `ymex`, `yashr`, `_yasc`,
  `is_gdpr`, `is_gdpr_b`, `yabs-sid`, до ~400 дней) **до выбора в баннере
  и вопреки явному отказу**. Причина: `<iframe data-src>` подхватывался
  общим ленивым загрузчиком сайта и к системе согласия привязан не был.
  Норма: ч. 1 ст. 9 152-ФЗ + обещание раздела 7 Политики о незагрузке
  скриптов при отказе.
- **(Б) Битрикс24** грузился сразу после **любого** выбора, включая отказ,
  и писал `b24_crm_guest_pages`, `b24_crm_guest_utm`,
  `b24-analytics-counter-16-view`.

Метрика гейтится **корректно** — только после согласия, её логику не трогали.

Владелец выбрал **вариант А+Г**: привести поведение сайта к уже написанному
тексту Политики, **текст Политики не менять**. Сделано:

- карта заменена заглушкой с кнопкой «Показать карту», адресом и внешней
  ссылкой на Яндекс.Карты; при согласии грузится сразу, при нажатии
  «Принимаю» — без перезагрузки. Клик по кнопке — **разовый показ,
  согласие в localStorage не переписывается** (решение подтверждено
  пользователем);
- загрузка Битрикса отложена до первого открытия попапа с формой; форма
  доступна при любом выборе (приём заявок — законный интерес).

Проверено локально (59 автопроверок, Playwright, зеркало прода):
три состояния согласия, локализация заглушки ru/en/cn, 1280×720 и 360×740,
отрисовка формы Битрикса. Все зелёные.

⚠️ **Открытие про выкладку:** отдельного `js/cookie-banner.js` на сайте
**нет** — запрос отдаёт 404, баннер минифицирован **внутрь `app.min.js`**.
В README прошлых патчей (`cookie-banner/`, `cookie-banner-i18n-fix/`) это
описано неверно. Поэтому нужно либо пересобрать `app.min.js` из исходников

⚠️ **Правовое основание патча было ошибочным.** Пользователь запросил
ссылку на норму, обязывающую разместить кнопку отзыва cookie-согласия —
такой нормы в праве РФ нет. Принцип «отзыв не сложнее, чем дача» взят из
GDPR (ст. 7 п. 3) и ошибочно подан как требование 152-ФЗ. Реально
п. 8 ч. 4 ст. 9 требует лишь указать в согласии **работающий способ
отзыва** — у сайта это почта, описанная в Политике, то есть норма уже
исполнена. Документы исправлены (README патча, оба чек-листа,
changelog); в память записано правило про опору только на право РФ.

Патч остаётся **полезной практикой** и попутно чинит реальный баг —
локализацию баннера на en/cn (он никогда не переводился). Решение о
выкладке — за владельцем, приоритет низкий. Если выкладывать: футер
продублирован на каждой странице, в README перечислены все 14 страниц,
нужна полная пересборка. После деплоя — чек-лист из README: отзыв после
accept и после decline, удаление cookie Метрики, локализация ru/en/cn,
регрессия формы Bitrix24 и «ноль запросов до выбора».

**Открытый UX-вопрос по патчу** (поднят пользователем 2026-08-18, не
решён): название «Настройки cookie» обещает экран с тумблерами, а клик
лишь переоткрывает баннер — причём ссылка в футере, баннер внизу, а при
отзыве после «Принимаю» страница перезагружается и прокручивается вверх,
так что реакцию легко не заметить. Предложенные варианты: переименовать
по действию («Отозвать согласие на cookie») + видимое подтверждение;
показывать баннер модально; сделать настоящий экран настроек. Если патч
решат выкладывать — сначала закрыть это.

**2 и 3 — переходят с 2026-08-13 без изменений.** Патч для es-trans.ru — уведомление о переходе в Telegram/MAX
(вариант 3, согласованный с пользователем) — готов
(`sites/es-trans-ru/messenger-consent/`: JS + CSS + README) и передан
пользователю в чате. Клиент уже применил первую версию и задеплоил, но
по ходу проверки на проде вскрылись два бага, оба найдены по
скриншотам пользователя и исправлены в этой же сессии:

1. **Вторая ссылка в модалке не рендерилась** («Согласием на обработку
   данных» отображалось как обычный текст) — причина оказалась в
   хрупкой сборке `innerHTML`-строкой с двумя одинаковыми
   `class="messenger-consent__link"` подряд. Фикс: модалка теперь
   строится через DOM-методы (`createElement`/`appendChild`).
   (Первая версия объяснения причины была ошибочной — предполагался
   несуществующий скрипт-сканер локализации; пользователь прислал
   реальный `script.js` сайта и поправил: `data-lang` на сайте всегда
   прописывается вручную в коде, как в `cookie-banner.js`, никакого
   автосканирования нет.)
2. **Текст модалки не переключался вместе с языком сайта** (сайт на
   английском, модалка всё ещё на русском) — причина: функция перевода
   сайта `je()` (в `js/app.min.js`) применяется только один раз при
   загрузке страницы / смене `#languageSelect`, а модалка создаётся
   позже, в момент клика, и `je()` её уже не видит. Фикс: модалка
   переводит себя сама — свой словарь `TRANSLATIONS` (синхронизирован
   со значениями, которые сайт сам сгенерировал в `app.min.js` для
   `messenger-consent-1`…`-8`) + чтение `localStorage['language']`, того
   же ключа, что использует переключатель языка на сайте.

Оба фикса подтверждены Playwright-проверками на живом проде. Также
обнаружено (по присланному `script.js`): в реальном файле на сервере
клиента накопилось несколько дублирующихся копий блока
messenger-consent от последовательных попыток патча — в README
добавлена инструкция удалить все старые копии и оставить только
актуальную. Ждём, когда клиент обновит `messenger-consent.js` на
сервере финальной версией и передеплоит — после этого нужна ещё одна
Playwright-проверка по полному чек-листу из README (включая оба
фикса и языковое переключение).

Отдельно от messenger-consent: пользователь сообщил, что иконка MAX в
шапке сайта в Firefox отображается сплошным чёрным пятном. Причина —
хрупкая конструкция символа `#max` в `img/icons/icons.svg` (вложенный
`<svg>` с PNG-картинкой, обрезанной через `<clipPath>`+`<use>`),
внутренние id-ссылки которой Firefox не резолвит при вызове символа
через внешний спрайтовый `<use>` (Chrome резолвит, поэтому там иконка
выглядит нормально). Подготовлен патч
`sites/es-trans-ru/max-icon-fix/` — готовый PNG (получен рендером
того же символа в Chromium, где clipPath работает верно) + замена
`<svg><use></use></svg>` на `<img>` в разметке, CSS менять не нужно.
Передано пользователю, ждём применения на сервере и деплоя.

Cookie-баннер, Bitrix24-гейтинг и фикс пробела с cookie `bh` (Метрика)
— все три фичи проверены end-to-end на живом проде, без изменений с
прошлой сессии. Универсальный шаблон cookie-баннера в
`sites/cookie-banner-universal/` — без изменений.
