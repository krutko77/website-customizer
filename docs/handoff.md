## Как устроена память проекта

Весь контекст проекта живёт в четырёх файлах. У каждого — одна роль.
Читай их **в этом порядке**:

| # | Файл | Отвечает на вопрос | Как меняется |
|---|------|--------------------|--------------|
| 1 | [project-brief.md](./project-brief.md) | **Что** это за проект и **зачем** | Редко (меняется суть проекта) |
| 2 | [state.md](./state.md) | **Где мы сейчас** и **что делать дальше** | Постоянно — это «живой снимок» |
| 3 | [changelog.md](./changelog.md) | **Что уже сделали** (по датам) | Только дописывается вниз |
| 4 | [decisions.md](./decisions.md) | **Почему** так, а не иначе | Только дописывается вниз |

Плюс [../CLAUDE.md](../CLAUDE.md) — инструкции по стеку, деплою и правилам работы.

**Правило, которое держит всё это в актуальном состоянии:**
после каждого осмысленного шага мы обновляем `state.md` + дописываем
`changelog.md` и **коммитим в git**. Поэтому история проекта = история
коммитов, а текущее положение дел всегда в `state.md`. Подробнее — в
разделе «ЖУРНАЛ ПРОЕКТА И КОММИТЫ» в `CLAUDE.md`.

## Быстрый старт для входящей нейронки

1. Прочитай 4 файла выше по порядку.
2. Глянь последние коммиты — это лента того, что реально делалось:
   ```bash
   git log --oneline -20
   ```
3. Если нужно увидеть, что менялось в конкретном шаге:
   ```bash
   git show <hash>
   ```
4. Посмотри, какие скиллы доступны — это основной инструментарий проекта:
   ```bash
   ls .claude/skills/
   ```
   Описание каждого — в [architecture.md](./architecture.md).
5. Возьми первый пункт из раздела «Следующие шаги» в `state.md` — и продолжай.

Cookie-баннер на `https://es-trans.ru/` работает end-to-end: показывается при первом визите, блокирует Яндекс.Метрику (включая сам `tag.js`, не только `ym('init')`) и форму Bitrix24 до согласия/выбора, корректно обрабатывает «Принимаю»/«Отказаться», решение сохраняется в `localStorage`; подтверждено повторно 2026-08-17 — до выбора **ноль** внешних хостов и **ноль** cookie. Согласие во всех трёх формах сайта работает корректно на всех страницах (18/18 форм проверены Playwright-ом). Универсальный шаблон в `sites/cookie-banner-universal/` (README + html/scss/js) готов к копированию в новый проект. Появился переиспользуемый чек-лист аудита по 152-ФЗ редакции 2026 — `docs/checklists/152-fz-website-audit.md` (пункты помечены 🔍 «проверяется технически, метод указан» / 🧑‍⚖️ «нужен ответ владельца»), плюс пример его применения — `docs/checklists/audit-es-trans-ru-2026-08-17.md`. Репозиторий на GitHub: `github.com/krutko77/website-customizer`, ветка `main`, upstream-трекинг работает штатно.
**Что в процессе / недоделано:** Три патча по es-trans.ru ждут выкладки клиентом. **Свежий:** `sites/es-trans-ru/cookie-settings/` — точка отзыва cookie-согласия («Настройки cookie» в футере: чистит `localStorage`, удаляет cookie Метрики, заново показывает баннер) + починка локализации баннера на en/cn; локально 19/19 сценариев зелёные, клиенту нужно заменить `js/cookie-banner.js` и добавить пункт в футер **на всех 14 страницах** (полная пересборка — футер продублирован постранично, список в README патча). **Два старых, обратной связи нет с 2026-08-13:** `sites/es-trans-ru/messenger-consent/` (модалка о переходе в Telegram/MAX; оба бага уже исправлены — DOM-сборка вместо `innerHTML`, свой `TRANSLATIONS` + `localStorage['language']`; клиенту нужно ещё удалить накопившиеся дубли блока в `script.js`) и `sites/es-trans-ru/max-icon-fix/` (замена хрупкого SVG-символа `#max` на `<img>` с PNG). После деплоя по каждому нужна Playwright-проверка по чек-листу из README. **По коду замечаний из аудита 152-ФЗ больше не осталось** — оставшееся требует ответа владельца сайта: уведомление в РКН и запись в реестре операторов, где физически лежит база заявок (российский ли тенант Битрикс24), договор поручения на обработку с Битрикс24, фиксируется ли факт согласия (дата/IP/версия текста) в `sendmail.php`, регламент реагирования на утечку (24 ч / 72 ч, ст. 21), назначен ли ответственный за обработку ПДн, рабочий ли ящик `info@es-trans.pro` (он же на чужом домене `.pro` вместо `.ru`, а это единственный канал отзыва согласия), перечень ПДн в политике шире реально собираемого формами (ст. 5, минимизация). Технический хвост: канонический `sites/es-trans-ru/cookie-banner/cookie-banner.js` отстал от прода — надо синхронизировать с версией из `cookie-settings/`. **Где живёт прод (URL / SERVER_ID):** Не задеплоен (в рамках этого репозитория). **Главные подводные камни:** **Попапы с формами и футер продублированы в разметке КАЖДОЙ страницы es-trans.ru** — общего include нет, поэтому правка одного шаблона без полной пересборки расходится не на весь сайт (именно так первая выкладка правки форм 2026-08-17 попала только на одну страницу из шести). При правках форм/футера проверять все страницы: сравнить `last-modified` и искомый фрагмент разметки по списку. **Любой динамически созданный элемент на этом сайте не переводится** — функция `je()` в `js/app.min.js` отрабатывает один раз при загрузке страницы и при смене `#languageSelect`, а элемент создаётся позже; наступили уже трижды (messenger-consent, cookie-баннер), лечение всегда одно — свой словарь `TRANSLATIONS` + чтение `localStorage['language']`. **Канонические файлы в `sites/es-trans-ru/` могут отставать от прода** (так и обнаружился `cookie-banner/cookie-banner.js`) — перед правкой сверяться с реальным `app.min.js` с прода, а не доверять репозиторию; `grep` по нему отваливается по таймауту, куски тянуть точечно через python3. Формы живут в скрытых попапах — Playwright не кликнет напрямую («outside of the viewport»), нужно через `page.evaluate` форсировать `display/visibility/opacity` у родителей, иначе получаются ложные ❌.
